# Match the work Deck actually draws before comparing frame cost

Edwin chose to build visual parity before a direct speed comparison. This task adds an explicit native compatibility mode and a validation gate. It enables TASK-0092 to compare frame cost under a later eligible BENCHMARK.md revision only after both windows show equivalent work. Revision 3 is frozen but ineligible because its reader actions occur before the pane opens. The existing uncapped native mode remains the separate test of whether every selected note can be placed.

## Definition of Done

- [x] The current production Glass renderer exports reproducible checkpoints for the frozen real and 10,000-note placed subsets. Each checkpoint records the window and field viewport, visible canonical note keys, card and tile rectangles, band and apparent detail, visible text fields, reader body and local links, and relevant navigator or other application chrome. Evidence: the valid real r12 and generated r6 captures, their hashes and the opt-in command in the README; the real reader checkpoint contains the `PHASES.md` body and local link.
- [x] The native compatibility mode uses the same placed identities, bands, ordering and production depth projection at declared checkpoints. Its drawing and hit testing use the same transformed bounds. It does not apply a hidden second cap, omit content or silently alter the normal uncapped native mode. Evidence: the hash-checked slot and card-field inventory, Rust hit-bounds tests, `native-compat-geometry-*-r6.json` and their checker reports. Both required fixtures pass initial and four checkpoint inventory checks. The real reader diagnostic blanks the held card at the recorded focus checkpoints; this still does not verify the native window's reader behavior.
- [ ] Side-by-side foreground captures at the same display scale and 1,440 × 900 window show matching visible populations and content detail for turn, hover, zoom, pull/locate and reader checkpoints on both required fixtures. Geometry tolerances and unavoidable text rasterization or chrome differences are fixed before scored runs and reported with their effect on comparability.
- [ ] The matched trace exercises equivalent delivered pointer, wheel and keyboard actions through each application's real event route. Named-key actions, reader/link state and action timing reconcile; late or skipped actions make a repetition ineligible for direct comparison.
- [ ] A parity verifier rejects a missing visible note, wrong rectangle/detail level, missing reader body or link, changed window/display, and incomplete action sequence. It retains the mismatched capture and reason. A task-specific verification note records a passing foreground check and these deliberate failures.
- [ ] The later eligible BENCHMARK.md revision's matched-work gate is demonstrably satisfied before TASK-0092 scores a direct speed comparison. The compatibility configuration, production and native build hashes, fixture and trace hashes, checkpoint summaries and screenshot hashes are retained. Any residual material mismatch is disclosed and blocks a direct speed claim.

## Steps

1. Record the actual production viewport and projection from `desktop/src/shared/slots.ts`, `desktop/src/shared/detail.ts` and the current `GlassField` at frozen trace checkpoints. Include production's navigator and reader layout in the visible-work inventory.
2. Choose one shared benchmark window composition and freeze it before timing. If application chrome cannot be made equivalent without changing normal renderer work, keep its cost visible in the report and do not call the run matched.
3. Add an opt-in native compatibility scene and camera using the production placed-subset fixture. Keep the uncapped scene untouched as the desired-experience workload. Draw production-equivalent card faces, quiet tiles, visible text, reader and links; route hit testing through their final bounds.
4. Drive the same OS-delivered input sequence and record state/capture checkpoints on both applications. Validate focus, display, viewport, event order, action lateness and reader body identity.
5. Implement the parity verifier and demonstrate its rejection cases before a scored run. Repeat the parity walk on the frozen largest real fixture and generated 10,000-note fixture; publish the accepted tolerance and all remaining visual differences.
6. Hand the validated compatibility mode and its provenance to TASK-0092. Do not use preliminary matched-subset diagnostics as a timing comparison.

## Verification and stop conditions

Create and link a task-specific test note when the comparison procedure exists. Its checks must read production-renderer checkpoints and native-window captures, not simply compare the exported fixtures. A source-only assertion that both sides received the same note keys does not prove visual parity. A deliberately displaced card, dropped tile, missing reader paragraph or delayed action must fail the gate for the expected reason.

Stop direct matched-work scoring if the actual visible populations, content, window composition or delivered input still differ materially. Record the mismatch and keep TASK-0092 open. Native uncapped diagnostics may continue under their separate label, but they never substitute for this direct comparison.
