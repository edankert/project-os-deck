# The visual parity gate rejects mismatched work

## Purpose

Check that the comparison gate refuses materially different visible work or incomplete actions before any direct timing result is scored.

## Procedure

1. Run `node --test prototypes/native-glass/tools/test-verify-parity.mjs` from the repository root.
2. When the native compatibility capture exists, run `node prototypes/native-glass/tools/verify-parity.mjs PRODUCTION_JSON NATIVE_PARITY_JSON NEW_REPORT_JSON` against each required fixture and action scenario. The production run must use `--measure-fixture-visual-checkpoints` and the same placed subset and eligible frozen protocol trace hash as the native run. Revision 3 is ineligible for scoring. The matched reader trace must display its local link without activating it.
3. Keep each result report and the captures identified in it. Repeat after any renderer or tolerance change.

## Expected results

- The automated mutations fail with the missing key, wrong rectangle, changed content, incomplete action or wrong display named. The unchanged in-memory comparator pair passes.
- A native run passes only if its foreground capture has the same trace, fixture, protocol, window composition, displayed identities and text, pane body and links, and timely complete actions as the production capture.
- A failure keeps the direct timing comparison blocked. A passing unit test does not establish that the native renderer has met visual parity.
