# Deck

## Goal

**This phase makes Deck a thing you can open.** When it opened, the repository held two designs, one feature and an architecture note, and no code. At the end of this phase a person launches Deck, sees this repository's notes listed as the cockpit lists them, puts the ones they are working on onto a desk, drags a panel onto a second monitor, and picks the same notes up on a tablet over the LAN.

Three words are used throughout and mean one thing each. **Deck** is the application this repository builds. **Spread** is its first view: notes as cards laid out across windows and screens, named after a comic spread. The **sidecar** is project-os-cockpit's Python service, which indexes the notes and answers questions about them; Deck consumes it from `../project-os-cockpit/` and never vendors a copy.

## Scope

- **The Electron shell.** Deck's own renderer, started fresh, sharing the main process concerns the cockpit already has: workspace discovery, terminals, windows and fleet health. Where Deck needs a piece of the cockpit's renderer it lifts that piece into a shared module without changing how the cockpit behaves.
- **The store.** One record of current workspace, focused note and current view, held in the Electron main process, with every window subscribing to it. Windows read from the store rather than each reading `localStorage` once, which is why two cockpit windows today never see each other change.
- **Windows.** Pop-out windows for the panels that already refresh on their own, window bounds remembered per window and placed by display, one focus window that owns navigation, and satellite windows that show state and never steal focus.
- **Spread.** Cards on a desk, driven by a list, several notes visible at once, several consoles, and a console the person can move. A **desk** is one arrangement of cards, saved and restorable.
- **Spread is judged as a thing a person uses, not as a grid that renders.** Added 2026-09-07: Edwin accepted the review's finding that the built application does not yet demonstrate Spread ([[REFERENCE-PHASE-0001-REVIEW]]). What it shows is a flat grid of identical cards with a reader beside it, and nothing in it can be arranged, grouped or searched in a way that differs from the cockpit. Six things are added to this phase to close that gap. **One:** the groups the sidecar already sends are drawn rather than flattened away, so what is owed comes first, phases hold their features and tasks, severity bands and test tiers are headings, and finished work folds away. **Two:** the list and the desk become two surfaces, with a navigator listing the view and a desk that starts empty and holds what a person put on it. **Three:** cards are moved with the pointer and removed, and where a card was left is what the desk saves. **Four:** a popped-out window carries one panel, which is the Needs-you strip, a note, or a desk. **Five:** the renderer owns search and filtering, because a pooled DOM hides an undrawn note from the browser's own find. **Six:** a card's face depends on its type, showing progress for phases and features, severity for issues, and staleness for tests.
- **Addresses.** Every reachable Deck state has one: a view, a desk, a focused note. A layout is then a list of addresses plus geometry, which is what makes it serialisable and drivable from the command line.
- **Views come from a provider, not from a fixed list of buttons.** The renderer asks a view provider which views the current workspace has and draws whatever comes back. The only provider built in this phase is the project-os one, and it offers the same views the cockpit's navigator does. The seam exists so that the Vault phase can add a provider that reads a vault's `.base` files without touching the renderer. The sidecar is not asked to change: Edwin decided on 2026-09-06 that the list of views is Deck's concern, revising the architecture note's proposal that the sidecar answer the question.
- **Two hosts, one renderer.** Deck runs its own HTTP host, which serves the renderer and proxies reads to the sidecar; the Electron window loads from that host too, so both hosts run identical bytes ([[ADR-0001-Deck-Serves-Its-Own-Read-Only-Host]]). Shell-only capability — pop-out windows among it — is detected through the preload bridge and simply absent when Deck is served.
- ~~**Reads only.** Every verb Deck offers goes through the sidecar's existing guarded endpoints. Deck adds no write path of its own.~~ **Reversed 2026-09-08.** Edwin asked for the opposite: "The deck needs to have the same functionality as the cockpit, so it needs to be able to write ... set state/property of a note and check check-boxes in the content of a note." [[ADR-0003-Deck-Writes-Through-The-Shell]] settles where that write runs. The first half of the sentence still holds and is now the whole rule: every verb Deck offers goes through the sidecar's existing guarded endpoints, called from Deck's main process over loopback. What is reversed is the second half.
- **Deck writes, from the shell, and the served host never does.** Added 2026-09-08. A write travels from the renderer through the preload bridge into the main process and out as a loopback request to the sidecar. Deck's HTTP host still answers 405 to every method that is not a read, and the capability set gains `write`, false when served, so a tablet is offered no verb at all — absent, not disabled ([[ADR-0003-Deck-Writes-Through-The-Shell]]; Edwin, 2026-09-08: "the tablet does not write"). Two verbs prove the path in [[FEAT-0013-The-First-Write]]: ticking an acceptance criterion with evidence, and one status transition read from the sidecar's actuator rows. Everything else the cockpit can do stays [[PHASE-0004-Parity]]'s.
- **A view is a description, not three fields of code.** Added 2026-09-08. What a view selects, how it groups, which band a note stands in, what a card shows and which surface may draw it become sections of one document ([[FEAT-0012-A-View-Is-A-Description]], [[ADR-0004-A-View-Is-A-Description]]). The description language is Deck's own, seeded with the Bases subset measured in Edwin's vault so that every base file he has written already reads as a description, and carrying a version number and an extension namespace from version one — because, as he put it, the subset "is a subset which we know cannot represent everything ... we will need to be able to extend it probably significantly". The project-os provider emits seven descriptions equal to today's views, so nothing a person sees changes on the day it lands.
- **Deck keeps its own index of the workspace's notes.** Added 2026-09-08. The main process reads the Markdown itself, parses the frontmatter, keeps a record per note and watches for changes ([[FEAT-0011-Decks-Own-Index]]). Edwin decided this rather than asking the cockpit for a records endpoint: "Decks own index, the Decks application are individual applications/views." The sidecar is still read for the navigation groups, the rendered note, the context, the statistics and every write.
- **The address grammar and the panel vocabulary open.** Added 2026-09-08. `surface`, `page`, `flow` and `step` join the grammar, each refusing an unknown value; panel kinds come from a registry each phase adds to rather than from a closed list of three ([[TASK-0052-The-Grammar-Opens-And-The-Panels-Come-From-A-Registry]]). This is what keeps "every reachable state has an address" true when Glass adds a surface and Parity adds pages.
- **Flows are written down as a concept and nothing is built.** Added 2026-09-08. A flow is an ordered list of steps, each with a done-state read from the record and a verb from the registry, and the only state outside the record is a cursor. `docs/ARCHITECTURE.md` carries the shape; the store reserves the cursor slot. Edwin said the same day that he does not yet know what flows should look like and wants them considered now and fleshed out over time, so this phase reserves the seam and builds nothing.
- **The adoption table.** `docs/reference/cockpit-adoption.md` is re-read against the cockpit's capability register whenever the cockpit ships a change note, and the rows Spread relies on move from `not yet` to `adopted` as they are built.

## Out of Scope

- **Glass**, the three-dimensional field where depth carries priority. That is [[PHASE-0002-Glass]] and it needs this phase's store and addresses first.
- **Obsidian vaults**: the workspace profile, bases as views, and `.canvas` files as boards. That is [[PHASE-0003-Vault]]. Only the seam is built here, and the seam is the view provider the renderer asks.
- **Rebuilding the cockpit's own renderer.** The cockpit stays the primary place for new functionality and takes its own work; Deck tracks it through the adoption table.
- **Writing JSON Canvas, or writing any file Obsidian owns.** Spread keeps its desks in Deck's own store, in Deck's own format.
- **A full local application on the tablet.** The tablet is served by the Mac's sidecar and reads; packaging the sidecar for iPadOS is a project of its own and is not started here.
- **What needs attention in a world**, deferred to [[PHASE-0003-Vault]]. Deck's front plane renders whatever the sidecar's owed-items answer returns and names no project-os obligation of its own.

## Where this stands

**2026-09-09: everything a machine can do is done. Every task in the phase is `done`, and what is left is four walks and a review.**

All eighteen tasks the widening of 2026-09-08 added have landed, and so have the two defects that were open. Seven of the eleven exit criteria are ticked. **The two open defects were both mis-diagnosed in their own notes, and saying so is part of the record.**

[[ISS-0023-Two-Sidecars-For-One-Repository-When-The-Paths-Differ-Only-In-Case]] was real and is fixed: Deck compared two path strings where it meant to compare two directories, so macOS's two spellings of one home directory made Deck start a second sidecar on a repository the cockpit was already serving. Three places decide "is this the same repository" and all three now ask the file system. [[RISK-0001-A-Second-Sidecar-Takes-Over-Focus-Routing]] closes again, on the check it was waiting for.

[[ISS-0022-The-Smoke-Run-Says-A-Popped-Out-Desk-Never-Draws-A-Card]] was **not** a defect in the renderer, and neither of the two candidate causes in its note was right. `npm run smoke` carried no `--workspace`, opened none, and then ran the panel checks against a workspace Deck did not know — so a card put on that workspace's desk changed a state whose `workspaceId` was `null`, and the count stayed at zero. ## Notes

**Why there is no separate foundations phase.** The Electron shell, the store, the read-only sidecar consumption and the two-host rule are all inside this phase rather than in a phase before it. Splitting them out would produce a first phase whose exit criterion is "a window opens and shows a note", which nobody can judge as a milestone, and it would strand the two rules that must hold from the first line of code — one renderer with two hosts, and views taken from a provider rather than a fixed list of buttons — in a phase that ends before any view exists. The three measurements this phase is judged on already are the foundation: same notes as the cockpit, a window that survives a restart on a second display, and the renderer opening on a tablet. If the phase later proves too large to steer, the split point is the first criterion: everything up to Spread showing the same notes as the cockpit is one phase, and windows plus the tablet host are the next.

**Dependency outside this repository.** Everything here rests on the sidecar in `../project-os-cockpit/`, which is not vendored. This phase still asks nothing new of it, and after 2026-09-08 that is a stronger claim than it was: Deck reads the sidecar's existing endpoints, writes through its existing guarded endpoints, keeps its own index rather than asking for a records endpoint, and owns the list of views. Two things the cockpit does not serve are still owed by it and are filed there the day the Deck task that needs them starts — a vocabulary payload (the status bands, the severity order, the known types) and a guarded property write. Until then Deck pins its copies by fixture and offers no property editor.

**Deck serves its own renderer.** [[ADR-0001-Deck-Serves-Its-Own-Read-Only-Host]] settles how the two hosts are built. The sidecar cannot serve an outside bundle without a change to the cockpit, and the cockpit is not changed for Deck, so Deck runs its own host and the Electron window loads from it too.

**One hazard is open.** [[RISK-0001-A-Second-Sidecar-Takes-Over-Focus-Routing]]: a sidecar Deck starts on a repository the cockpit already has open takes over the `.cockpit/url` file that routes the `cockpit` command. The mitigation is in [[TASK-0007-The-Sidecar-Starts-And-Stops-With-Deck]], which reuses a running sidecar instead of starting a second one.

**Sequencing inside the phase.** The store comes first because every window subscribes to it, pop-out windows come next because they are the first visible change, and Spread comes last because it is the first thing a person judges.

**Order.** Deck, then Glass, then Parity, then Vault, decided by Edwin on 2026-09-07 ([[ADR-0002-Glass-Is-The-Main-View]]), revising the order of 2026-09-06 that had no parity phase ([[REFERENCE-SURFACE-ARCHITECTURE-OPTIONS]], Part 8, item 2).
